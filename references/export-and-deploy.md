# 导出与上架：让任何 RAG 平台直接吃你的切片

## 核心洞察

上一轮调研犯了范围收窄的错误——我按「平台必须原生支持父子结构」筛选，
结果只剩 FastGPT 和 Dify。但换个问法：

> **如果每个文件本身就短于平台的默认分段长度，那平台怎么切，都是它自己。**

实测数据：

| 指标 | 值 |
|---|---|
| 切片数量 | 241 条（父块） |
| 字符数 最短 | 76 |
| 字符数 中位 | **175** |
| 字符数 最长 | 912 |
| 主流平台默认分段 | 500 ~ 1000 字 |

**中位 175 字，最长 912 字，全部小于默认分段长度。**

所以：把切片导成「一条条文一个 .md 文件」，上传后平台分出来**一个文件恰好等于一个 chunk**，
父子结构被完整保留。不需要 API 导入，不需要平台支持父子结构。

→ **几乎所有 RAG 平台都能用**：RAGFlow、MaxKB、AnythingLLM、FastGPT、Dify、
Cherry Studio、WeKnora、Open WebUI……

## 为什么这个思路成立

关键不是"文件不多不少刚好一个 chunk"，而是：

1. **切片天然是结构化的**。条文本身就是一个完整的语义单元，不是从长文本里切出来的碎片。
2. **长度天然受控**。规范条文的长度由立法体例决定，不会出现"一段 5000 字"。
3. **元数据头自带溯源**。每个文件第一行就是「规范名｜章｜节｜第X条｜小标题」，
   模型读到它就知道自己在引用哪一条——不需要平台的 metadata 字段。

> 一句话：**把结构信息写进文本，就不依赖平台的结构化能力。**

这是"以内容换结构"的工程取舍。代价是元数据头占几十字、会重复；
收益是零适配成本，任何平台都能用。

## 导出什么

`export/export_for_platform.py` 一次生成三种格式：

| 输出 | 内容 | 适合 |
|---|---|---|
| `markdown/` | 241 个 .md，一条条文一个文件 | 任何支持上传文件的平台（最通用） |
| `分段文本/全库.md` | 单文件，`## 第X条` 分隔 | 支持"按标题分段/Title Chunker"的平台 |
| `json/slices.json` | 结构化切片（父块+子块+metadata） | 自写脚本、灌任意向量库 |
| `json/fastgpt_pushdata.json` | FastGPT `pushData` 格式 | FastGPT API 导入 |

### 每个 .md 文件的内容

```markdown
《建筑防火通用规范》GB 55037-2022｜7 安全疏散与避难设施｜7.4 公共建筑｜第7.4.1条｜公共建筑安全出口与疏散楼梯｜强制性条文
公共建筑内每个防火分区或一个防火分区的每个楼层的安全出口不应少于2个；……
1 除托儿所、幼儿园外，……
2 除医疗建筑、老年人照料设施……符合表7.4.1规定的公共建筑。
【表7.4.1 仅设置1个安全出口或1部疏散楼梯的公共建筑】
| 建筑的耐火等级或类型 | 最多层数 | 每层最大建筑面积（m²） | 人数 |
|---|---|---|---|
| 一、二级 | 3 | 200 | 第二、三层的人数之和不大于50人 |
……
```

**必须包含三部分**：
1. 元数据头（可溯源）
2. 条文正文 + **全部款**（不漏款）
3. 关联表格（已渲染成 Markdown 内联）

缺任何一部分都会导致某类问题答不出来。

## 平台选择建议（修正版）

| 场景 | 推荐 | 理由 |
|---|---|---|
| **快速演示，不想折腾** | **MaxKB** | Docker 一条命令；全中文；上传 md 即可 |
| **要好看的界面给领导看** | **FastGPT** 或 **Dify** | 产品成熟、界面漂亮、全中文 |
| **文档解析能力强** | **RAGFlow** | 但它的强项（PDF 解析）我们用不上 |
| **只想自己调检索** | 自写 50 行 Python + Chroma | 全可控，最适合做评测 |

**修正**：上一轮说"RAGFlow 不做首选，因为不能导入现成分块"——
这个结论只在我们坚持"必须原样导入 761 个切片"时才成立。
既然一个 .md = 一个切片，RAGFlow 直接上传文件夹就行，这个障碍消失了。

## 部署前必须确认的两件事

1. **分段长度设大一点**。比如平台默认 500 字，而我们的最长切片是 912 字——
   这一条会被切开。**把分段长度调到 1000 以上，或按换行/空行分段。**
   这是整个方案唯一的失败点，务必检查。

2. **验证导入后条数对不对**。上传 241 个文件，检查平台显示的 chunk 数是不是 241。
   如果是 300+，说明有文件被切碎了，把分段长度调大重来。

## 如果平台按换行切分

有些平台用 `\n` 作为分隔符，会把一个文件切成十几个 chunk。
这种情况下改用 `分段文本/全库.md` + 「按标题分段」模式，
或者把每条条文内部的多行合并成一行（牺牲可读性换结构完整）。

## 一句话总结

**别去找"支持父子结构的平台"，去找"能把一个文件当一个 chunk 的平台"。**
后者容易得多，而且我们的切片长度天然满足条件。
