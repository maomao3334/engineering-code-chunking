# 验收题设计：期望值先核实，再谈命中

> 这一篇是血的教训。**在真实项目里，验收题写错比检索调错更常见，而且后果更严重**
> ——它会把你稳定地导向错误方向，还给你一个"在改进"的假象。

## 核心原则

> **期望条文必须对着语料库原文核实，不能凭印象、不能凭"这条看起来应该管这事"。**

三次实测翻车（同一部规范、同一个项目内）：

| # | 我写的期望 | 核实后的真相 | 后果 |
|---|---|---|---|
| 1 | 消防车道净宽净高**4.0m**，在 GB 55037 第 3.4.5 条 | 3.4.5 只写"应满足消防车安全、快速通行的要求"；**4.0m 不在 GB 55037 里**，出自 GB 50016 第 7.1.8 条 | 差点为了让题"全对"去调检索，等于教系统编造 |
| 2 | 店面贴软包墙，应落 **6.5.3** | 6.5.3 只管"避难走道/疏散楼梯间/消防电梯前室"三个部位的 A 级要求，**商铺墙面不在其列** | 期望值本身就是错的，题目无解 |
| 3 | 小孩培训班，应落 **4.3.4** | 4.3.4 只讲"布置楼层"（能不能在地下、在第几层）；问"要不要隔开"更贴 **7.4.3**（安全出口和疏散楼梯独立设置） | 期望指向了错的那一面 |

三次都不是检索问题，都是**我把"这条看起来相关"当成了"这条就是答案"**。

## 怎么核实（可操作的检查）

写进题单前，对每个期望条文做这四步：

1. **把该条原文完整读一遍**，不看标题、不看摘要
2. **反向自问**：问句里的每一个关键词，这条正文里有对应内容吗？
   如果问"隔开"而正文只讲"第几层"，就是没对上
3. **全库搜关键词**，确认没有更贴的条：`grep 软包`、`grep 隔开`、`grep 培训班`
4. **允许"一题多正解"**，写进期望的是集合，不是单条

```python
# 期望写成集合，命中任一即算过
want={"7.4.3", "4.3.4", "4.1.3"}
hit = bool(want & set(top3_clauses))
```

## 一题多正解是常态，不是例外

第 11 题核实后的正确答案是**三条组合**：

| 条文 | 管什么 | 回答问句的哪一面 |
|---|---|---|
| **4.3.4** | 儿童活动场所布置楼层（不在半地下、按耐火等级定层数） | "能放几层" |
| **7.4.3** | 高层建筑内儿童活动场所的安全出口和疏散楼梯**应独立设置** | "要不要隔开" ← **最贴题** |
| **4.1.3** | 哪些场所需要防火门窗 + 2.00h 防火隔墙 + 1.00h 楼板分隔 | "怎么隔" |

一个含糊问题往往横跨多个条文。**如果验收时只认一条，就会把"答得更全"判成"答错了"。**

## 第 7 题的正确处理（示例）

问题：「店面装修想贴软包墙，消防上让不让？」

**错误做法**：把期望写成 6.5.3，然后调检索让 6.5.3 上来。→ 把系统调歪。

**正确做法**：承认这一题在 GB 55037 里**没有唯一对应条文**，改判分口径：

| 判分点 | 合格标准 |
|---|---|
| 是否引到第 6.5 节（内部装修材料） | 必须 |
| 是否说明关键不是"能不能贴"，而是**该部位材料的燃烧性能等级** | 必须 |
| 是否给出 A 级 / B₁ 级的具体适用条件 | 加分 |
| 是否直接答"可以贴/不可以贴"而不谈等级 | **不合格**（典型外行答法） |

这样判，程序命中 6.5.5（歌舞娱乐场所装修材料）虽然是"相邻条款"，但**只要它讲清了燃烧性能等级逻辑，就该给分**。

## 验收题的结构模板

每题最少五个字段，缺一个就会在复盘时说不清：

```python
dict(
    n=11,
    cat="D情境",
    q="小孩上培训班那层，跟楼下商铺要不要隔开？",
    want={"7.4.3", "4.3.4", "4.1.3"},       # 集合，命中任一即算召回
    keys=["独立设置", "防火分隔"],            # 答案里必须出现的关键结论词
    kuan=None,                               # 多款题的款数要求；单款题不填
    refuse=False,                            # 域外题填 True
    note="最贴题的是 7.4.3（独立疏散），不是 4.3.4（布置楼层）",  # 写清为什么这么判
)
```

`note` 字段最容易被省，但它正是下次复盘时唯一能救你的东西。

## 自动判分的四个维度

只看这四条，别用"感觉像对"：

| 维度 | 判什么 | 抓什么毛病 |
|---|---|---|
| `hit` | 期望集合与 top3 有交集 | 检索跑偏 |
| `keys` | 关键数值/结论词是否**出现在答案里** | 合成环节丢字、漏款（比"看起来对"可靠得多） |
| `kuan` | 多款题答案的款行数 ≥ 期望 | 全款交付 |
| `refuse` | 域外题必须明确拒答 | 编造 |

**`keys` 是最有价值的一维**。因为"命中条文"和"答案正确"是两件事：
检索命中 2.1.2，但合成时只说了 3 款，答案就是错的——这种情况 `hit` 是过的，只有 `keys`/`kuan` 能抓住。

## 域外题：什么是合格的拒答

| 回答 | 判定 |
|---|---|
| 「现行规范未就此作出规定」 | ✅ 合格 |
| 「请补充层数、面积、使用性质等信息」 | ✅ 合格（问题确实无法判断时） |
| 「我是 AI，无法判断」 | ❌ 不合格（把责任推给身份，用户拿不到任何信息） |
| 凭常识给出一个答案 | ❌ 不合格（最危险） |

域外题的合格线是**必须全对**，因为它是唯一能挡住"编得像"的防线。

## 报告里必须写"语料库边界"

每次跑完验收，报告里要有一节说明**哪些题不是系统的问题**：

- 「4.0m 不在本语料库（在 GB 50016），程序不报 4.0m 是正确行为」
- 「款数大于期望值正常：跨条引用、关联表格、跨库互补都会追加段落」
- 「表格题款数为 0 正常：答案主体是 Markdown 表格」

不写这一节，每次汇报都要被问一遍"为什么这题不答"，而且容易被误解成能力不足。

## 一条反直觉的结论

**发现验收题写错，比发现检索错更有价值。**

前者说明你的判分口径在变准；后者只是排名在变。这一轮三题里，
两题（第 7、11）核实后**改的是期望值而不是代码**——这本身就是产出。
