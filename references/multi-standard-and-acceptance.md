# 多部规范并库 + 验收题自动跑分

> 这是第二轮实践补上的两块内容：**怎么把第二部规范（含"法规"这种不同编号体系）并进同一个库**，
> 以及**怎么把切分质量验收写成可重跑的自动脚本**（而不是人工对照）。
> 实战出处：GB 55037-2022（241 条）+《高层民用建筑消防安全管理规定》（51 条）= 292 条 / 940 切片。

## 一、为什么要并第二部

技术规范（GB）是**设计标准**，不管"电动自行车能不能停在楼门口""占用消防车道怎么罚"这类**使用期**问题。
只有一部规范时，这些问题的正解只能是「规范未规定」——**这是语料缺项，不是检索失败**，
但会被误判成系统不行。

判断标准：如果验收题里出现「管理/使用/处罚/物业/维护」类问题，就说明需要并一部管理规定。

## 二、怎么并（不改检索代码）

**关键：父子块靠「条文号」这一个键来串。** GB 的条文号是 `12.0.6`，法规的是 `第三十七条`，
两者天然不冲突，所以**直接把法规的行追加到同一个 xlsx 的两个页签里**，检索代码一行都不用改。

追加位置（列序必须严格对齐原 `10_build_xlsx.py`）：

| 页签 | 追加内容 |
|---|---|
| `语料库` | 规范全称/编号/章/节/条文号/小标题/正文/…/关联表格（留空） |
| `RAG切片` | 父块 1 行（整条）+ 子块 N 行（按 `（一）（二）` 或段落） |
| `表格明细` | 法规一般没有表，不用动 |

实现参考：`rag/build_kb_v6.py`
（数据源用 `import_law.py` 已经切好的 md，每个文件第一行就是元数据头，正文在第二行起，
比重新解析纯文本可靠得多）。

产出文件名要能被版本号自动选择逻辑匹配：`*语料库_v*.xlsx`（如 `消防规范语料库_v6.xlsx`），
程序取版本号最大的那个，不需要改代码。

## 三、三种"款"的写法都要认

| 来源 | 款的写法 | 正则 |
|---|---|---|
| GB 规范 | `1 内容；` | `^(\d+)\s+` |
| 部门规章（列项） | `（一）内容；` | `^[（(]([一二三四五六七八九十]+)[）)]` |
| 规范化后 | `（1）内容；` | `^[（(](\d+)[）)]` |

一条正则统一：`^\s*(?:(\d+)\s*|[（(]([一二三四五六七八九十]+|\d+)[）)]\s*)(\S.*)$`
**并且要求行尾是句读**（`；。，：）`），否则会把"2022 年…"这类正文误判成款号。

## 四、条文号渲染：`第X条` 不能重复套

法规自己的条文号已经是 `第三十七条`，如果代码里统一写 `f"第{clause}条"`，就会渲染成
「第 第三十七条 条」。正确做法是加一个渲染函数：

```python
_CLAUSE_NO = re.compile(r"^第[一二三四五六七八九十百零\d.]+条$")
def cite_no(clause):
    c = str(clause).strip()
    return c if _CLAUSE_NO.match(c) else f"第{c}条"
```

所有拼接处（依据段、跨条引用、"以上共 N 款"）都走这个函数。
同理，答案里的**条号抽取正则**也要两种都认：

```python
_CITE_GB = re.compile(r"(\d+\.\d+\.\d+)")              # 12.0.6
_CITE_CN = re.compile(r"第([一二三四五六七八九十百零]+)条")  # 第三十七条
```

## 五、并库后必须补的两件事（否则法规条文永远排不上来）

### 1. 口语同义词要覆盖"使用期"说法

问「小区消防车道总被私家车占着」，正文里没有"私家车""占着"，只能靠"消防车道"四个字去撞，
结果第 3 章一堆设计条文（3.4.1~3.4.7）把第 12 章 12.0.2 压到第 4 名。

加映射（`rag/synonyms.json`）：

| 口语 | → 规范术语 |
|---|---|
| 私家车 / 占着 / 乱停 | 不应存放机动车辆、占用、阻塞、保持畅通 |
| 堆了东西 / 堆放 / 被堵 | 不被占用、堵塞、禁止堆放物品 |
| 电动车 / 电瓶车 | 电动自行车、停放、充电、公共门厅、楼梯间 |
| 怎么处理 / 处罚 / 罚款 / 违法 | 责令改正、罚款、法律责任、消防救援机构 |

### 2. 章节路由加权（实测最有效的一招）

问「疏散通道被堵了怎么办」，第 12 章 12.0.6（使用与维护）只有一句话，
字面上打不过第 7 章一堆设计条文。做法：**问句里出现使用期标记词时，
第 12 章和法规条文乘 1.35 权重**。

```python
USE_MARK = ("占用","被占","占着","堵","堆放","堆了","停放","停车","充电",
            "检查","处罚","罚款","违法","物业","管理","维护","怎么处理","怎么办")
# header 含「第12章」「使用与维护」「应急管理部令」→ 加权
```

实测效果（同一问法、同一检索器，只加了上面两条）：

| 问题 | 期望 | 修复前 | 修复后 |
|---|---|---|---|
| 小区消防车道被私家车占着 | 12.0.2 | 第 4 名（12.72） | **第 1 名（61.75）** |
| 电梯前面堆了东西 | 12.0.6 | 未进前 8 | **第 1 名（36.70）** |
| 疏散通道被堵了怎么处理 | 12.0.6 | 第 5 名 | **第 1 名（52.53）** |
| 电动车能不能进电梯 | 第三十七条 | 未进前 8 | **第 1 名（42.59）** |

调试方法：把命中排名和分数打出来（`rag/debug_misses.py`），不要靠猜。

## 六、跨库互补：第 2 条命中来自另一部规范时，把正文也带上

问「高层住宅疏散通道被堵了怎么办」，GB 规范只有"应保持畅通"一句，
真正的管理依据在《高层规定》第二十八条。模板合成时只在"另可参考"里列个条号是没用的——**要把正文带出来**：

```python
# 第 2 条命中与第 1 条不同标准 → 追加其正文
for h in others[:1]:
    hp = r.parents.get(h["clause"])
    std2 = hp["header"].split("《")[1].split("》")[0]
    if std2 and std2 != std_name:
        parts.append(f"【同时可依据《{std2}》{_cite(...)}】"); parts.append(hp["body"])
```

这样"技术规范 + 管理规定"才会一起交付。

## 七、验收题自动跑分（这一节最重要）

人工逐题对照会漏、会不一致、下次改代码没法重跑。
**把验收题写成带期望的结构化用例，用脚本跑**：

```python
CASES = [
  dict(n=1, cat="A多款", q="建筑防火应达到的目标要求有哪几个方面？",
       want={"2.1.2"}, keys=["保障人身和财产安全","公共利益","节约资源"], kuan=4),
  dict(n=17, cat="F拒答", q="装修用的石材台面多少钱一平米？", refuse=True),
  ...
]
```

判定口径（三条一起看，缺一不可）：

| 维度 | 判什么 | 为什么 |
|---|---|---|
| `hit` | 期望条文是否在 top3 命中里 | 检索层 |
| `keys` | 关键数值/结论串是否出现在答案里 | **合成环节有没有丢字**（比"看起来对"可靠） |
| `kuan` | 多款题答案里的款行数 ≥ 期望 | 全款交付 |
| `refuse` | 域外题必须明确拒答 | 防编造 |

输出：每题一条 `正确 / 部分正确 / 错误` + 一份 md 报告（逐题答案 + 问题清单 + 语料库边界说明）。
实现参考：`qa/accept20.py`。

**报告里一定要写"语料库边界"**，否则每次都被问"为什么这题不答"：

- 4.0m 消防车道净宽**不在 GB 55037**（在 GB 50016 第 7.1.8 条），程序不报 4.0m 是正确行为，报了就说明在编造
- 款数大于期望值（如 8/5）正常：跨条引用 + 关联表格 + 跨库互补都会追加段落
- 表格题款数为 0 正常：答案主体是 Markdown 表格

## 八、一个反直觉的教训

**验收题本身可能是错的。** 第一版第 7 题写"7 款含 4.0m"，逐字核对后确认 4.0m 根本不在本规范里。
如果当时为了让题"全对"去调检索，就会把系统调成"必须报 4.0m"——**反过来教它编造**。

正确做法：发现期望值有误，改验收题并标注「实测纠错」，同时在报告里说明为什么这样才对。
