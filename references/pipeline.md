# 完整流水线

以 GB 55037-2022《建筑防火通用规范》为实例。约 74 页 PDF，241 条条文，全程一次性跑通约 5 分钟。

## 步骤

### 1. OCR（双遍 + 逐行择优）

规范多为扫描件，且**正文与表格字号不同**，单遍 OCR 一定会丢东西。

| 设置 | 用途 |
|---|---|
| 300dpi 全篇 | 主体正文 |
| **600dpi 局部重识别** | 300dpi 置信度低的行、字号偏小的表格区域 |

**择优规则**：同一行取两遍中置信度更高的结果。实测一部规范有 5 条低置信度条文（<0.90）需要 600dpi 补识别。

**输出**：`p001.txt`… 每页一个文本文件 + `lines.json`（带每行 y 坐标与置信度）。
y 坐标必须保留——后面判断"这一行属于哪个标题下面"要靠它。

### 2. 行重建

OCR 按物理行输出，但一条条文常被折成 3~5 行。需要按版面把行拼回语义行：

- 用 y 坐标判断间距，间距明显变大 → 段落断开
- 行尾不是 `。；：` → 大概率还没完，继续拼
- 页码行、页眉、页脚整行丢弃

### 3. 结构化解析

按编号形态切层级：

```
3 建筑总平面布局                    ← 章（行首单个数字+空格+无标点结尾）
3.4 消防车道与消防车登高操作场地     ← 节（N.M）
3.4.5 消防车道应符合下列规定：       ← 条（N.M.K）
1 道路的净宽度和净空高度应…；        ← 款（行首数字+空格+以；或。结尾）
```

**关键判断**：款必须"行首是数字"且"句末是 `；` 或 `。`"。少了句末判断会把正文里"不小于 2 个"这类当成款。

### 4. 表格单独解析

表格**不混入条文正文**。

- 定位：PDF 页面上有横线框的区域，或文字流里出现的明显列式排布
- 提取：行列坐标 → 单元格值
- **合并单元格按语义展开**（跨行表头要补到每一行）
- 原表里表示"不适用"的横线（`—`）**不得解释为 0**

### 5. 上标下标与特殊字符修复

OCR 几乎必然会错这几类，必须逐条对照原页修复：

| 正确 | OCR 常见错法 |
|---|---|
| m²、m³ | m2、m3 |
| B₁、B₂（燃烧性能等级） | B1、B2 |
| Ⅰ Ⅱ Ⅲ（罗马数字） | I II III、1 2 3 |
| ℃ | °C（对比同类规范时视为等价） |

实测一部规范需要修复 62 条。

### 6. 人工核对

不是全篇重看，只核这几处：

- OCR 置信度 < 0.90 的条文
- 编号是"推断补齐"的条款（原页有编号但 OCR 没识别出来）
- 上标下标修复过的地方
- 涉及数字、单位、等级的条文

### 7. 切片

三种切片：

| 类型 | 内容 | 数量（示例） |
|---|---|---|
| 父块 | 整条条文（含元数据头） | 241 |
| 子块 | 每一款 | 520 |
| 表格块 | 每张表（父条号指回引用它的条文） | 4 |

### 8. 质检

见 [quality-gates.md](quality-gates.md)。

## 踩过的坑

| 坑 | 后果 | 怎么发现的 |
|---|---|---|
| 只跑 300dpi | 表格里的小字整片丢失 | 与参考库比对，4 张表的条文字数明显偏少 |
| 表格并进正文 | 溯源文本被污染，无法引用原文 | 字段说明里"条文原文本体"定义被破坏 |
| 款号 OCR 丢失后静默补齐 | 补错了查不出来 | 与参考库比对时条号对不上 |
| 把 `第4.1.4条` 当成新条起点 | 条号错乱 | 条号连续性检查失败 |
| 未设节的章写成"0 节" | 章节结构与目次对不上 | 章节数量核对 |

## 与参考库比对

如果手上有同规范的其他版本（比如别人做的 Excel、或官方电子版），**逐条比对是最高性价比的质检**。

实测：236/241 完全一致；5 条差异全部可解释（1 条 ℃ 与 °C 等价、4 条对方把表格内联进了正文）。
这种"差异可解释"的结论，比"我们自己检查了一遍"有说服力得多——尤其对领导汇报。
